# 拟人运笔：研究笔记 → 实现规则

目标：观看绘制过程时像人画的，不像机器人逐行光栅。成品精度红线不变（uncovered=0、
均值/可见差持平、同种子可复现）。规则来源见文末资料。

## 一、当前算法的"机器感"清单（对照代码诊断）

1. 笔尖沿一笔**匀速**走（app `tipAt` 按弧长线性插值）——真人运笔是钟形速度
   曲线：起笔收笔慢、中段快（minimum-jerk）。
2. 曲线处不减速——真人沿曲线画时按 v∝r^(1/3) 减速（三分之二幂律）。
3. 同组扫带**等距平行**（step 固定，独立抖动仅 ±0.11step）——真人推进间距
   是相邻相关的漂移，不是独立白噪声。
4. 同组每条带**都从同一端起笔**（u 恒从小到大）——真人来回刷（蛇形）。
5. 扫带是**单弓弯的近直线**——真人长扫是手臂弧线 + 沿途漂移。
6. 每笔落笔时长严格按长度线性——真人有节奏抖动（有的快有的慢）。
7. 换阶段停顿固定 420/700ms——真人停顿时长不等。
8. 大色块直接从一侧等距扫满——真人**先勾边后填心**（cutting-in）。

## 二、落地规则（改动点）

### app.js 播放时间维（不动成品像素，成品 = u≥1 全笔绘制）
- R1 钟形速度：`tipAt` 加每笔缓存的时间→弧长弯曲 LUT；速度形 = 0.30+0.70·sin(πf)^0.9
  （端点不设 0 速度，避免停死；实测 s(0.25)=0.20、s(0.75)=0.84）。总时长不变。
- R2 曲线减速（相对直线归一）：直段全速 1.0，弯段按绝对半径 0.135·r^(1/3) 减速
  （r≈30px → 0.44×，夹 [0.32,1]）。纯匀曲率笔归一化后仍是线性——那部分慢由
  R2b 弯笔时长权重承担（管线 weight ×(1+0.30·(1−弦长/弧长))，弯笔总时长更长）。
- R3 节奏抖动：每笔落笔时长 × (1+0.36·(hash−0.5))，高斯感、按笔序种子化；
  阶段内仍按权重归一，总量不变。
- R4 停顿变化：换阶段停顿 300–620ms（点睛 480–900）、收笔 700–1200ms，逐笔种子化。
  仅 artist 算法启用；cover/pyramid 节奏照旧。

### js/pipeline.js 几何/顺序（影响成品，回归验证）
- R5 相关漂移：扫带推进偏移改成相邻相关的随机游走 drift（步进 ±0.25·step，
  夹紧 ±0.2·step），替代独立抖动。
- R6 方向交替：同组相邻扫带起笔端交替（蛇形），减少抬笔跳转；由组级种子定
  首带方向。
- R7 弓弯拟人：主弓弯幅度随带长增长（长带 = 手臂弧线），叠加第二谐波低频漂移，
  幅度仍夹紧在带内（zoneGid 裁形不变）。
- R8 先勾边后填心：平涂大类块（flatArt、ph1、面积>2600px²）先用窄笔
  （≈0.42×半宽，夹 2.0–6.5px）沿组轮廓内缩描一圈，再等距填心。
  颜色 = 组色，zoneGid 裁形，成品边界不变差；对精度有利（边缘覆盖更准）。
- R9 四遍推进（平涂通路）：`ph0` 起稿铺满——背景宽笔铺中间色（同色斑纹/噪点一起铺）
  + 每元素沿长轴一层主色底（近似色，noCover+noZone 不记覆盖/占位）+ 大色块精确落笔；
  `ph1` 整片细化背景（大色带先、就近收拾窄带噪点，不做网格扫描）；`ph2` 按元素块
  一处画完再走（大形已立：中块色→深描边→细线，文字块"字形→描边→装饰"）；
  `ph3` 前景遮挡/点睛。起稿结束整幅基本成形，不允许全画面东一块西一块。
- R10 元素块局部完成：前景按 bbox 邻近并成块（飞机/标题/每行文字），块内
  “填色大形 → 深色描边 → 细线高光”，文字块"字形→描边→装饰"；块间按主档/次要/细节
  三档，同档内种子随机。随机只改合格块序，不改四遍结构和“块内画完再走”。
- R11 画家·过程版（独立算法 `algo:'painter'`，2026-10-31）：与"准确复刻"共用观察/裁剪/记账，
  只换作画组织——人画流程：遍1 铺满背景（约 25 支超大蛇形宽笔把 washMask 一口气盖满，
  中间色、noCover、几秒完成——用户明确要求"背景一下子铺满、后续才细化、然后才画前面"）；
  遍2 细化背景（bgAll 整片精确 paintFull，大色带先、窄带噪点就近收拾）；遍3 画主体（先全图
  落大形：mass 组 `paintBlobRough` 松排带 1.45×；再逐对象完成：`paintBlobFinish` 勾边+补缝+
  宽带兜底 → 填充→深线→浅线 → 对象内查漏 residualComp）；
  遍2 逐对象完成（对象=bbox-gap 元素 + 线组接触重挂；收形 `paintBlobFinish` 勾边→补缝→
  宽带兜底 → 填充→深线→浅线 → 对象内查漏 residualComp(ph=1)）；遍3 点睛（tier3）；
  遍4 收笔（共用全局残补，ph=3）。对象切换 +260~520ms"看"停顿（挂在对象第一笔 ms 上），
  手位 chainNN 串对象。照片/无背景家族图自动回退现有流程（order='phase'）。
  实测：海报 19029 笔/6.388/2.77%，插画 4972 笔/1.873/0.50%，与画家模式同级；
  铺满拍 25 笔约 5 秒盖满整片背景、主体留白（dev/stg/ph-s3-s3-p0done.png），
  细化背景结束黑框/暗角收完（ph-s3-s3-p1done.png）。

### 不改的
- 分区/取色/掩膜/零贡献审计/补漏/残差机制（成品精度框架）。
- cover/pyramid 旧算法全程节奏。
- 种子语义：所有新增随机都走 srnd/hash 种子流。

## 五、结构笔：把"整圈框/整条字边"还给手（2026-11-01）

诊断（s3 海报、805×1024 应用解码像素）：

- 黑框其实是**一个闭环组**（gid 0，55,271px，平均带宽 15px）。旧逻辑按块面
  扫带刷（bandHalf≈73px），可见墨迹被裁成 587 段贴在四边，中位笔长 16.5px，
  分布在 ph1（461 段）+ ph2（126 段）——回放里就是"框画一半去干别的"。
- 红字边：37,538 个红像素被分割成 1,127 个色块（最大 375px），逐块画共
  3,416 笔、中位 5.9px，撒在整个 ph2。
- 根因不止是分组碎：一笔的脊线可以横跨整幅、靠裁剪蒙版只留两小截墨迹，
  手不可能同时按在相隔几百像素的两处（"瞬移+虚线"）。

落地：

1. `ringPlan/paintRing`：面积/周长估带宽 ≤34px、骨架闭环 ≥周长 50%、bbox
   覆盖画幅 ≥55% ⇒ 画框。沿骨架闭合路径整圈一笔（+平行黑边顺手续上），
   四角缺口按连通块就地补；结构笔时间轴 ×10 权重，排在铺底之后第一位。
2. `structs/paintStructPass`：相邻像素的组均色差 ≤36 的组并查集并成结构；
   只收"墨线"（luma<150 或 sat>0.45）、宽 ≤16px、骨架 ≥30px、面积 ≥60px 的结构
   （奶油字心/飞机这类块面留给填色遍）。每条结构沿骨架一笔走到底，
   按颜色跳变（ΔE>12）与 120px 长度断段，段间重叠 1 点、连续发出；
   段色取段内主色块原色，跨块像素按 zoneTol=12 记账，差得多的当场补。
3. 时序：wash(ph0) → 画框(ph1 首) → 背景刷准(ph1) → 描边(ph2 首，画主体) →
   填色(ph2，对象内也是先线后块) → 点睛/收笔(ph3)。

实测（s3 app 像素、seed 3、fid5）：

- 黑框 587 段 → 1 条主笔 + 1 条平行边 + ~30 个角点补笔，全在 ph1 开头连续完成；
  浏览器 seek 序列里边框黑像素 0→899→6,229→…→27,419 逐步绕满一圈（约 5.6–8.7s）。
- 红字边结构 95 条 / 717 笔（原 3,416 笔），覆盖 85% 红像素；浏览器里
  f 的红边从 45.0%→49.8% 连续描完，随后 50.8% 才开始填奶油色。
- 质量：5 种子 mean 6.637–6.653、gt24 3.088–3.124%、uncovered=0（基线
  6.618–6.635 / 3.084–3.098，偏差 ≤0.03/255）；artist 笔流 sha1 不变；
  engine_check 17/17；cover/pyramid md5 不变；browser_check 0 白点 0 报错。
- 瞬移指标（一笔墨迹 ≥2 块且相距 >max(30,4w)）：107/23,044 = 0.46%，
  主要是 ph0 的 25 条铺底宽扫带（本来就从主体后面扫过），ph1/ph2 仅 91 笔。

## 六、铺满整页 + 黑框一圈 + 字先框后色（2026-11-01，第二轮）

诊断（用户看回放后的反馈："蓝底要是我画就会一次性把整页填满，不会给字预留位置；
黑框按一个方向一笔画完，之后不用再碰"）：

- 旧 ph0 的 wash 被 `washMask` 裁在蓝像素内：页面里 26.1% 的字/框位置一个像素都没刷过，
  等于"先给字留了白"；随后 ph1 用 11,941 笔、约 35 秒把蓝区重刷准确。回放是
  "带字洞的蓝底 → 黑框 3 秒 → 回头刷蓝 30 多秒 → 45% 才出现字"。
- 旧 ring 主笔覆盖 54,653/55,271=98.9%，随后 31 笔小补（凸起/四角），观感仍是没一笔画完。

落地：

1. `paintBlueFlood`（ph0）：蓝色版面 bbox 内按 24px 条带蛇形扫完；条带内按"纯蓝芯"
   （3×3 全蓝）切色段，字/框列空出来，再用左右两段颜色按 ~60px 线性过渡刷过去
   ——字的位置也盖成蓝底，且不会留下字的轮廓。每条刷完就地补该条里 >24 且 ≥8px
   的蓝色斑块（混色边不补，留给字）。版面最外一圈（RIM=24px）不强制记账，留给
   `edgeGroups` 用原图逐组色收边（时间轴压到 2ms/笔，快速带过）。
   ph0 结束把蓝像素统一记成 covered，ph1 不再有"细化背景"。
2. `ringPlan/paintRing`（ph1）：框家族 = gid0 + 与框同色（色距 ≤45）且 55% 像素
   贴框 ≤6px 的深色组（内框线、扫描边线碎组），用组合掩膜裁形；路径统一顺时针、
   起点转到左上角，按四个角切成四段、首尾同点连续走（回放里是一圈，四角圆头
   一次压住）；角点按转角加宽（防折线偏移啃外角）。绕完 0 补笔。
3. `app.js`：painter 标签改 **铺满整页 / 勾黑框 / 画主体 / 点睛·收笔 / 落款**；
   权重 [0.18,0.05,0.74,0.03,0.03]。

实测（s3 app 像素、seed 3、fid5，5 种子）：

- 蓝底：ph0 覆盖 **100%** 蓝像素，字心抽样（大 f、AIR MAIL、飞机机身等）全部被 ph0
  的墨盖过；ph0 之后蓝区 0 笔；刷蓝从 11,966 笔/~35s 降到 ~4,100 笔（951 主刷 +
  548 补色 + 边缘收边）。
- 黑框：**4 笔**（四段）全在 ph1，框像素覆盖 **100%**，ph2/ph3 框墨 **0 笔**；
  起点左上角、顺时针。
- 时序（浏览器实测）：蓝底 0–17.5%、黑框 17.5–22.3%、字外框 22.3–31.5%、
  填色 31.5–94.2%、点睛/落款 94.2–100%。
- 质量（第二轮当时）：5 种子 mean 7.142–7.154、gt24 3.373–3.415%、unc=0、白点 0；蓝区
  6.5/1.55%（旧 5.5/1.24%），6px 低通 1.9/255（旧 0.93），肉眼一致。
  这是"整页一口气"的代价：扫描噪点不再逐组复刻，蓝底变成马克笔平涂。
- artist 笔流 sha1 不变（s1 290d1fd…、s3 54e6d7c…）；engine_check 17/17；
  cover/pyramid 3/3 md5 不变；导出 PASS；browser_check 0 白点 0 报错。

## 七、字心一次刷满：整块填充（2026-11-01，第三轮）

用户反馈："涂字里面的颜色的时候，颜色不像背景那样一下子就填好。"

诊断（`dev/_fill_tags2.mjs` / `dev/_fill_seq.mjs`）：
- 旧流程把每个大色块拆成两遍：ph2 开头 `paintBlobRough` 全图松排一遍（带间留缝、
  边不勾），走到对象时再 `paintBlobFinish` 收形。一个字心实际是"先出现半成品，
  75% 的片长之后才补齐"，回放里就是分两次涂。
- 字心组还常被标成 `soft/grad`（平涂背景分类器按"大、浅、暖"误判），
  填充走两级网点：一笔实色拆成两层互补点，看着像点涂不像刷。
- 另外这些元素在 `masses/rests` 两张表里重复出现，同一个元素会被走两遍。

改法（`js/pipeline.js` `paintHumanFlow`）：
- 删掉 `paintBlobRough` / `paintBlobFinish`，新增 `paintRegionFill(g,ph)`：
  沿组长边拉条带、按短边 2~4 道横贯 bbox 的宽笔，`zoneGid` 裁回组形；
  条带互相搭接，落笔即 100% 覆盖（`[fill] unc=0->0`）。平涂块用组均值实色，
  不再拆网点（软背景的网点只留给背景渐变）。
- 画主体不再"先松排再收形"：大色块按手位最近邻一块块走，每块 fill + 贴边碎块
  同一笔群；之后才收细碎组（元素内仍是"填充→深线→浅线"）。
- 同色/抗锯齿碎边按 **4 邻接** 并入主块的填充笔群（bbox 相交会带进别处的碎块），
  用 `paintRegionFill` 一并刷掉；字心落笔后不再留一圈蓝毛边。
- 硬上限坑：`emitPlan` 以 ph=0 发笔，`hardCap` 只拦 direct `emitStroke` 的表演笔；
  画家路径的填充笔不能查 `strokes.length >= hardCap`，否则整组一条带都发不出，
  全靠 `fillGaps` 兜（之前一次调试里 strips=0 就是这个原因）。

实测（s3 海报、fid5、seed3）：
- 字心：f 的 7777px 由 3 道 57px 宽条带一次刷满；43 个大色块共 241 道宽笔，
  整波约 470 笔（含碎边）。
- 完成度（`dev/_fill_curve.mjs`，奶油像素里"最终是奶油、当前还是蓝"的比例）：
  34% 100% → 38% 43% → 42% 9.7% → 58% 2.6% → 收尾 0.02%。
- 质量：5 种子 mean 7.159–7.177、gt24 3.407–3.433%、unc=0；蓝区 6.34/1.56%。
- artist 笔流 sha1 不变（s1 290d1fd…）；engine_check 17/17；cover/pyramid 3/3；
  browser_check 0 白点 0 报错；导出 PASS。
- 版本：app v69 / worker v58 / engine v37 / pipeline v56（b69）。

## 九、按对象作画：先描边再填满（2026-11-02，b71）

用户反馈（b70 回放）："蓝底和黑框正常，但字和飞机不正常。f 完全可以先把外面的红色
一笔描完，再把里面的色一下子涂全；飞机也是先把边缘描好再一下子填上。基本思路都是
先描边再涂满里面。"

诊断（`dev/_obj_probe.mjs` / `dev/_obj_conn.mjs` / `dev/_role_err.mjs`）：
- b70 的"画主体"是**全图先描边 → 再全部填色 → 再逐组收碎块**。分割层把 f 的红边
  切成 1,271 个碎组（中位 34px、737 个 <40px），结构笔只盖住 85%，剩下 15% 由
  `e.local` 逐组补：f 的红边实际 **1,210 笔**（143 结构笔 + 1,067 碎笔），碎笔散布
  在整个 ph2 甚至片尾；填色又和别的字交错。飞机同理（86 结构笔 + 上千碎笔）。
- 对象表用 bbox 邻近（gap≈10px）合并，海报整幅前景被并成 **1 个巨型对象**
  （2,580 组），"一个对象画完再下一个"名存实亡。
- 细边质量底线：每个 rim 像素用它所属组的均值上色时误差 16.47/255（= b70 的
  16.56）；整圈一个均值会到 24.6（红边暗沿/深蓝抗锯齿边被抹成红色）。

改法（`js/pipeline.js` `paintHumanFlow`，只动画家·过程版）：
1. **对象 = 前景组的像素 4 邻接连通块**（同一个字的描边与字心天然相连；字与字之间
   隔着蓝底，各自成块）。海报 38 个对象，f/飞机/各行字各自独立。
2. 对象内角色：字心（`fill`，颜色接近最大非线组）、细边（`rim`，色差大且
   `area/(0.5*(bw+bh)) <= 18`）、其它色块。细边还要"50% 像素在字心 5px 内"才算
   这一圈的描边（红字、别色字块不算）。
3. 描边：先沿**整条细边的 union 骨架**走一遍连续底笔（回放第一眼就是"一笔绕一圈"，
   不会因为颜色被切碎而变成虚线）；底笔用 `emitStroke` 发、`noZone/noCover` 不记账
   （底笔只是视觉层，后面各色档会按真实颜色盖一遍）。然后 rim 像素按颜色做
   **像素级加权 k-means（K=5：最亮/最暗/最蓝/最饱和/均值作初始锚点，7 轮）**，
   每档单独建掩膜、膨胀 2px 接断口后取骨架，沿骨架连续走；落笔裁在原掩膜里
   （不会画到蓝底）。按弧长 ~70px 分段、段间共享 1 个点，每段取这一段笔路在
   **原图上的真实均值**——回放里是一条连续笔，颜色不会被平均掉。
4. 补边：描边后、填色前，把所有还有未覆盖像素的细边候选（包括没通过贴边检查的
   蓝底抗锯齿碎边）按手位 `chainNN` 串起来，用 `paintRegionFill` 一条宽带刷满
   （1 笔/组），当场收完。
5. 填色：这个对象的字心组连续发出（`chainNN` 按手位），一组一次刷满，中间不插
   别的字。
6. 对象内查漏（正常 0 笔），然后才下一个对象。

实测（s3 海报、fid5、seed3）：
- f：描边 85 笔（一整圈）→ 补边 320 笔 → 填色 176 笔，全在 f 自己的时段内完成。
  浏览器帧确认：红边先绕一圈，随后奶油色从顶部整块刷满（`dev/stg/o4-f-*.png`）。
- 飞机：描边 91 + 补边 126 + 填色 383；同样"边缘先描好、里面一次填满"。
- 总笔数 **11,075**（b70 13,044，-15%）；质量 5 种子 mean **7.182~7.203**、
  gt24 **3.515~3.542%**、unc=0（b70 7.159~7.177 / 3.407~3.433）。
- 插画 s1：4,252 笔（b70 5,471）、1.817/0.503%（b70 1.812/0.501%）；照片 s2 走
  原流程不变（12,727 笔 / 10.798 / 7.717%）。
- artist 笔流 sha1 不变（s1 `290d1fd7…`、s3 `54e6d7cb…`）；engine_check 17/17；
  cover/pyramid 3/3；browser_check 0 白点 0 报错；导出 PNG/JSON/SVG/HTML/WebM PASS。

坑：
- 细边**不能**按"组均值的 luma"二分：红边的亮/暗差异沿字长变化，二分会把字切成
  上下两段，横截面还是被一个均值抹平。必须像素级聚类 + 分段取真实色。
- 补边必须放在**填色之前**，而且要覆盖**所有** rim 候选（含没通过贴边检查的），
  否则这些组会掉进 `inspectObj` 的逐组 `residualComp`：f 的查漏变成 1,140 笔、
  而且排在填色之后，正好复现用户说的"字填好了、红边还在后面冒出来"。
- 补边用 `paintRegionFill`（1 笔/组）而不是 `paintFull`（2~3 笔/组）：f 的补边
  599 → 320 笔，质量不变。
- 描边覆盖容差 `zoneTol` 太小（36）会留下 ~18% 记账未覆盖、补边变多；60 即可。
- 整圈底笔必须用 `emitStroke` 直接发：`emitPlan` 会按"零新增像素（noZone 下 zoneCov
  不动）"把整条底笔删掉，回放里还是虚线。
- 描边/补边/填色的笔都打了 `ob`（对象序号）调试标记，真机排查用。





## 十、插画/照片的过程修正（2026-11-03，b72）

用户反馈："海报很完美，但插画和照片太糟糕。" 逐图测（`dev/_diag_flat.mjs`）：
- 海报 s3：flatScore 0.545，`order='painter'`、`bgFill='blue'`，43 个对象，正常。
- 猫插画 s1：flatScore 0.909，`order='painter'`、`bgFill='wash'`；背景不是蓝的，
  走旧 wash + 逐组补准，ph1 有 2,559 笔背景笔。固定时间轴只给 ph1 5%，
  4 秒内刷 2,559 笔——回放里背景一闪而过，然后猫慢慢磨。
- 猫照片 s2：flatScore 0.197 → `flatArt=false` → `painterActive=false`，
  直接回退旧 artist 色区流程（`order='phase'`，10,174 笔），没有对象级。
  时间轴 ph2 32% 塞 7,541 笔（260 笔/秒），ph3 33% 只画 403 笔（30 秒慢动作）。

结论：海报的"完美"来自它恰好长成流程假设的形状（蓝底 + 大色块）；
插画/照片一个被背景补准的笔数拖累、一个根本没进新流程，外加固定阶段配比。

改法（只动 painter，artist/cover/pyramid 不动）：
1. **背景**：非蓝底平涂**不**用条带 flood。试过按主背景色族条带铺满，成品
   误差 1.87→2.14，渐变背景出现可见横向色带/接缝，已回退。保留 wash +
   逐组补准（1.811~1.903/255），只把阶段时间按真实笔数/落笔量分配
   （`app.js`：`bgFill==='wash'` 时动态 share，海报蓝路径仍用固定配比）。
2. **对象内部再分层**：细边拆成"外轮廓"（3px 内有对象外像素）和"内部细节"
   （被大面包住）。外轮廓先描 → 整块填满 → 内部细节（眼睛/嘴/腮红）最后。
   仅非蓝底启用；海报的字/飞机没有这两层结构，保持 b71 顺序不变。
   代价：s1 4,252→约 4,700 笔（fid5），成品均值不变。
3. **照片先铺近似底色**：painter 照片在色区之前按横条（约 6% 短边高）铺一层
   真实均值宽笔，`noCover/noZone` 不记账、不占位；后面的精确色区笔仍把每个
   像素重涂成原图色，成品逐像素不变。中途帧不再是白纸上的一块块色斑。
4. **照片阶段时间**：按每段真实笔数分（实测 s2：起形 1,394 / 铺色 835 /
   塑形 7,541 / 点睛 403），不再让塑形段 260 笔/秒糊成一片。

实测（fid5、seed1~5）：
- 海报 s3：10,959~11,030 笔，mean **6.955~6.961**（b71 7.18~7.20），unc=0。
- 猫插画 s1：4,657~4,750 笔，mean **1.811~1.903**，unc=0。
- 猫照片 s2：12,638~12,727 笔，mean **10.568~10.798**，unc=0；成品与 artist
  逐像素一致（只多一层 noCover 底），过程帧 40/70% 不再是白色空洞。
- artist 笔流 sha1 不变（s1 `290d1fd7…`、s3 `54e6d7cb…`）；engine_check 17/17；
  cover/pyramid 3/3；browser_check s2/s3 painter 0 白点 0 报错、unc=0。

坑：
- s1 的 ph1 那 2,559 笔**不是** ring：`[ring] total=0`，全是"细化背景"的
  逐组补准。改 ring 门槛/配色前后笔数完全不变——归因前先看 `[ring]` 日志。
- 条带 flood 在**渐变**背景上一定会留接缝：每条一个颜色、相邻条没有过渡，
  人眼看得出横向色带；除非能沿条带做连续渐变，否则不要再用它铺背景。
- 照片的近似底色必须 `noCover+noZone`：否则会把色区笔判成"已覆盖"而跳过，
  成品出现底色的粗糙色块。
- 桶/对象的时间配比按 `pN/pC` 算，`pC` 用每笔 `st.ms`；海报的蓝路径不要
  跟着换成动态配比，用户已经认可它的节奏。

## 十一、b73 实测：描边一笔 / 填色一刷 / 去海报特判

**用户反馈**：海报"完美"，插画和照片"太糟"；一个字母的描边明明能一笔完成却描了很久，
里面的填色要很多笔。

**诊断（数字来自 b71/b72 实测）**
- 描边：`paintObjOutline` 固定 70px 切段（`CHUNK=70`），再按颜色 K=5 分档、每档重新取骨架
  再切段；一个 f = 85 笔描边 + 320 笔逐碎片补边。
- 填色：`paintObjFill` 按碎片组循环，每组 `paintRegionFill` 固定 ~3 条带；f 的字心被扫描
  噪点拆成几十个组 = 176 笔。
- 特判：`paintBlueFlood` 写死"版面蓝"像素判据；`useSplit=!blueFloodOk` 让海报保持旧顺序；
  `bgFill='blue'|'wash'`；app 的固定时间表只给非 wash（海报）用。

**改法**
1. 描边：细边骨架按端点接成长链（同色才接），沿链只在"颜色真的变化"时断笔（连续 2 点偏离
   段均值 >12，或整段漂移 >20），平涂的一圈红边就是一笔；段色取这一笔实际盖住像素的均值
   （单色最优），偏色像素用 `zonePx` 按像素色不记账，紧跟其后的同色簇补边（cd=24）。
2. 填色：`colorClusters` 按颜色并簇（cd=8），联合掩膜一条横贯带（`halfW=span/2+2`）刷满，
   单组才退回原来的 `paintRegionFill`。
3. 误差守卫：对象画完后，把画布上偏差 >22 的像素按 4 邻接（同色才连）分块，每块最多两笔。
   笔数由真实误差区域决定，不按碎片组膨胀。
4. 去特判：`paintBgFlood(frameFam)` 用 `bgFirstPlan` 的主色家族（`famGid`）+ 可测量闸门
   （面积 ≥15%、铺满画幅 ≥60% 或贴 ≥3 条画布边、面积加权偏差 ≤12）；`bgFill='once'|'wash'`；
   删除 `useSplit` 闸门，所有对象统一"外轮廓→填满→内部细节"；`stats.exact/ring` 表示是否
   画了闭合外框；app 标签按 `ring` 显示"勾外框/补背景"，时间表统一按 `pN/pC` 动态分。
5. flood 的版面掩膜排除 `segPaper`（白纸底不刷背景均值，否则染成暖白）；画家路径的 ring
   不再查 `hardCap`（否则铺满+收边一多就永远画不到框）。

**实测（极致、5 种子）**
- s3 海报：7,747~7,795 笔 / mean 6.977~6.981 / 可见 3.1% / unc=0，`bgFill=once ring=true`
  （b72：10,959~11,030 / 6.955~6.961）。描边从每对象几十段降到 1~3 段链。
- s1 插画：1,964~1,974 笔 / mean 2.608~2.611 / 可见 0.54% / unc=0，`bgFill=once ring=false`
  （b72：4,657~4,750 / 1.811~1.903）；浏览器实测 1.36/255、可见 0.27%、0 白点（18.9% 白是纸）。
- s2 照片：13,003~13,092 / 10.568~10.798，与 b72 逐项一致（`order='phase'`）。
- artist 哈希：s1 `290d1fd7…`、s3 `54e6d7cb…`，与基线逐字符相同；engine_check 17/17；
  cover/pyramid md5 不变；browser_check s1/s2/s3 0 白点 0 报错；painter s3 导出全 PASS。

**坑（下次别再踩）**
- `forceKeep` 只加在 `emitBand` 的 **zone 分支**。加到公共 spread 会把 artist 的零增益笔留下，
  artist 哈希立刻变（本次就是这么发现的）。
- `zoneTol` 的比较对象也不能全局改成像素色：结构笔（artist）按组均值，改成像素色会动哈希。
  用 `opt.zonePx` 只在描边启用。
- `covered` 的"几何覆盖"同理，用 `opt.geomCover` 只在描边启用；否则收尾查漏的语义变了。
- 一笔一个颜色无法同时复刻亮芯和暗边：用"这一笔实际覆盖像素的均值"最小化误差，剩下的
  交给误差守卫；不要用中心线色（误差更大），也不要用组均值（跨色组时是折中色）。
- 用"对象剪影外轮廓"描边在细边碎片化时会断成几十个闭环，反而不如"骨架接链"。
- "贴画布边"判据对带黑框的海报无效（蓝底被框包住，不贴边）→ 必须补"铺满画幅 ≥60%"。
- 白纸底（s1）不能整体刷背景均值：flood 的版面掩膜要排除 `segPaper`，否则纸被染成暖白。

## 十二、b74 照片分层（多尺度笔触 + 误差驱动）

**问题**：插画/海报已经像人画，照片还是"色块拼贴"。误差图显示 52% 的误差集中在
高梯度区（毛发、石缝、轮廓），而每一笔是整条 12~15px 带的均值，把毛发的明暗
压平成硬边色斑；且 2,915 个色区各自一个均值，相邻色区的均值差 10~20 就是一条
可见拼接线。实测（s2，极致）：13,092 笔 / mean 10.798 / >24 7.72%。

**参考**：Hertzmann 1998《Painterly Rendering with Curved Brush Strokes of Multiple
Sizes》——由粗到细多层笔刷，每层只在"当前画布与参考图差得够多"的地方落笔，
笔向沿图像结构（梯度法线/等照度线），颜色取该笔覆盖区域的原图色。本项目的区别：
我们已有色区框架保证覆盖与精确取色，所以不重写字区，只在主遍之后加"误差驱动层"。

**实现**（只走 `painterFlow && !flatArt`，artist 照片逐字节不变）：
1. 主遍笔宽收窄：`bandHalf` 照片分支 = `clamp(bw*0.55, 2.6, 7.5)*fidScale`；`sweepAt`
   对照片也按 56px 分段取局部均值（`localColor`），云/毛发/石墙有明暗层次。
2. `paintPhotoLayers()`：4 层 `h=[8.4,5,3,1.8]*scaleB`、`T=[21,16,12.5,10]`，
   总预算 11,000 笔。候选点按网格扫描，笔向 = 结构张量切线（`flowX/flowY` 存 2θ），
   低相干时随机角；笔身是 3~4 点微弯胶囊，颜色 = 笔身覆盖像素的原图均值。
3. **每笔先算增益**：逐像素 `gain += err_before - err_after`（最大通道差），
   要求 `gain > 0.75/px` 且没有任何像素变差超过 22；否则不发笔。落笔用
   `forceKeep+noCover+geomCover+noZone`：跳过"零覆盖"检查，但按几何记账覆盖，
   查漏不会把它重涂回组均值。
4. 位置在"主遍之后、查漏之前"；查漏只兜真正的漏网像素。
5. 试过但回退：按误差加权的笔色（偏向离群亮点，mean 9.47 更差）；
   用模糊参考图给色区笔取色（拼接线少了，但边缘发糊，mean 10.00，退回）；
   把 <420px 的碎色区完全交给细化层（覆盖不足，查漏补 2,942 笔，mean 9.40 更差）。
